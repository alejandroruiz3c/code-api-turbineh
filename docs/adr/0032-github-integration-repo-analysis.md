# ADR-0032 · Connect GitHub and integrate into the client's repository as a verified pull request

- Status: accepted
- Date: 2026-10-12
- Context: PLAN §16.5 P5. Until now `POST /v1/plans/{id}/pull-request` and `GET /v1/repos` took a token from the
  user per request, were tested only against a mocked GitHub, dropped the package under `turbineh/<slug>/` without
  adapting it, and the result screen's "Integrate into repository" needed a GitHub sign-in that invitation access
  does not have. Owner priority: integrating into a client repository must cause zero extra work for the coding
  agent or person — the PR must arrive clean, verified and self-explanatory, stating exactly what is left.

## Decision

### Connect GitHub (optional, per workspace)

- A dedicated OAuth flow on the existing OAuth app (`GITHUB_CLIENT_ID/SECRET`), separate from sign-in, bound to the
  access workspace: `GET /api/github/connect` → GitHub → `GET /api/auth/callback/github/workspace` (under the app's
  registered callback path).
- **state**: 32 random bytes in an httpOnly, Secure, SameSite=Lax cookie scoped to the callback path; the server
  stores only its SHA-256 (one use, 10 minutes). The callback requires cookie == returned state and the stored row.
- **PKCE (S256)**: verifier stored encrypted with the state, sent only in the server-side code exchange.
- **Workspace binding**: the state row names the workspace; a browser whose access cookie is another workspace is
  refused. The CLI (`turbineh connect github`) gets a one-time link (10 minutes, hash stored) and a short code shown
  on both the terminal and the page before continuing to GitHub.
- **Minimal scopes**: `public_repo`; `repo` only when the user chooses private repositories (the UI explains why:
  GitHub has no narrower OAuth scope that allows pull requests on private repositories).
- **Token**: AES-256-GCM with `DELIVERY_TOKEN_KEY` (as deliveries), never returned, never logged. "Disconnect GitHub"
  deletes it and revokes the grant at GitHub. Agents/CI can connect with a token (`POST /v1/github/token`), stored
  the same way.

### Repository analysis (`ops.repo-analysis.turbineh`)

Through the API, no clone: file list, root manifests, workspace `package.json` files, then the application's
configuration. Detects app folder (monorepo), framework/version, App/Pages Router, `src/` layout, aliases, package
manager and lockfile, auth library, ORM with schema, migrations folder and database-client module, database, UI
libraries, Tailwind, test runner, lint/format, scripts, CI, env file **names**. The reader itself refuses env files,
keys and registry credentials. Compatibility, conflicts and adaptation decisions are code (never a model) and
travel in the plan (`plan.repository`) and the PR.

### Adaptation and pull request (`deploy.github-pull-request.turbineh`)

- The package lands in its own folder in the project's source root (`src/turbineh/<capability>/`, app folder in a
  monorepo); imports inside it are relative (self-contained), the project's alias is used for its modules; the
  project's Drizzle client is reused; Security Pack basics are copied only when imported; Jest projects get the
  capability's vitest tests renamed `*.vitest.ts` so their suite is not broken.
- Merges: dependencies with exact versions, existing entries never changed (no downgrades, differences reported);
  `.env.example` gets names plus the package's explanatory comments (never values); tables registered with one
  line in the project's Drizzle schema; the migration generated by the project's own drizzle-kit config in the
  sandbox (or a SQL migration in the capability folder for projects without Drizzle); the lockfile updated by the
  project's package manager in the sandbox. Unrelated files are never touched (checked on the final PR diff).
- One commit per logical step on `turbineh/<capability>` (code, glue, schema, dependencies, settings, lockfile,
  migration); draft PR whose body has summary, the project as analysed, decisions and why, differences, files,
  commits, verification, limits, **what the reviewer must configure** (required settings separated from optional
  ones with defaults, the project's migration command, install) and how to revert.
- **Verification inside the project**: the PR head is downloaded by commit (no token in the sandbox), secret files
  and escaping symlinks removed, then the sandbox runs install (registry only, install scripts disabled — no
  third-party code runs while there is network; git/URL dependencies refused before), then without internet:
  install scripts, typecheck, lint, the project's tests, the capability's tests, migration applied to a throwaway
  PostgreSQL, production build; plus "only planned files changed" and gitleaks on the changes. Placeholders only
  for the project's own documented settings; the capability's optional settings keep their documented defaults.
  The PR is marked ready and the state becomes `integration_verified` **only when every check passes**; otherwise it
  stays a draft listing each failure, whether it points at the capability's files or the project's own, and the
  next step. Never merged. GitHub Free private repositories cannot hold draft PRs: the title says `[Draft]` until
  verified.

### Adaptation model

Quality over cost here: glue that cannot be derived deterministically (e.g. reusing a database client exported as a
factory) is written by the strongest documented open coder among the configured Backup Coder slots — **GLM-5.2**
(the only open model in the independent SWE-rebench top 5: 62.9 % at $1.40/problem [indep.], `../knowledge/modelos-ia/
02-multimodal-y-especializados/codigo-y-agentes.md`) — with DeepSeek-V4-Flash-0731 as automatic fallback
(`ADAPTATION_MODEL_ORDER=primary-first` reverses them). Newer models listed in the knowledge base (GLM-5.3,
DeepSeek-V4.1-Flash, MiMo-V2.6-Pro) are not served by the configured EU provider today and lack independent
SWE-rebench results; adopting one is a provider decision for the owner. Output must match a contract (e.g. export
`db`), carries `// turbineh:generated-backup`, contains no provider names, and goes through the same verification;
if unavailable or invalid, a deterministic fallback is used (and its extra dependencies are added only then).

## Consequences and limits

- Package managers: pnpm, npm and Yarn classic; Bun and Yarn Berry are reported as unsupported. Private registries
  cannot be installed (credentials never enter the sandbox).
- The install phase has network without an egress allow-list; the guarantee is that only the package manager runs
  (scripts disabled, registry pinned). An egress proxy is the next step.
- Checks use placeholder settings and a throwaway database; third-party services are not exercised.
- Wiring the capability into the client's pages stays with the reviewer or their coding agent; the PR names the
  entry points and `agent/INTEGRATE.md` explains them.
- Draft → ready uses GitHub's GraphQL mutation; if it fails the PR stays a draft and the result says so.
