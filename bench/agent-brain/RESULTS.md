## After (2026-10-13, branch `feat/agent-brain-speed-2`, ADR-0046)

What changed, measured with the same 54 conversations (3 in parallel), shipped runtime loaded from the worktree:

1. **Templated reply after a confirmed action** (component `ai.orchestrator.turbineh`): an explicit yes/no to a
   pending action is settled by code without the decider; when the confirmed tool succeeds the reply comes from a
   template (the tool's `message`, else the confirmed summary plus the reference in the result), with no model call.
   A failed action still goes to the model.
2. **Per-attempt timeouts** for runAgent model calls (15 s, `AI_ATTEMPT_TIMEOUT_MS`; a stuck attempt is retried
   once, transient errors keep their two retries) and for decisions (5 s, `AI_DECIDER_ATTEMPT_TIMEOUT_MS`, one
   retry; before: one 15 s attempt).
3. **Gateway hedging** (`apps/web/src/server/ai-gateway.ts`): implemented, tested and measured on staging at 3.8 s
   (~gemma p90), one hedge per request, per-app daily budget, billed on the answer only. **Shipped off by default**
   (`AI_GATEWAY_HEDGE_AFTER_MS=0`): it fired on 2–6 of ~140–180 chat calls per run and **never answered first** in
   the valid runs, so it did not improve p95/max (rule: keep only what does).

### Reading

- **Success**: 54/54 in every valid run, no regression by kind.
- **Model calls saved**: the template answered 43 of 43 confirmation turns per run: chat calls 181 → 137–141
  (−23 %) and decider calls 121 → 76–80 (−35 %) per 54 conversations; confirmation turns went from p50 1.26 s to
  ~0 s (tool time; the bench's tools are in-process).
- **Same day, production gateway, runtime only** (`control-main-prod-gateway` → `control-after-runtime-prod-gateway`):
  turn p50 2.37 → 2.34 s, p90 4.85 → 4.20 s, p95 6.72 → 4.66 s, max 11.96 → 9.37 s; cost 2.08 → 1.40 USD per 1,000
  conversations (−33 %). Non-confirmation turns also improved (p95 7.62 → 5.20 s, chat-call max 7.20 → 4.78 s);
  part of that is run-to-run variance, part is the per-attempt timeout bounding stuck calls.
- **End to end on staging** (`after-turbineh-staging-r1/r2`): p50 2.39/2.33 s, p90 4.46/4.50 s, p95 4.88/4.83 s, max
  9.01/10.91 s, 1.36/1.44 USD per 1,000 conversations (1.38/1.46 counting cancelled hedges at their upper bound).
- **Hedging**: no gain. With the old runtime it fired on 6/178 calls and won 0 (`control-main-staging-gateway` p95
  8.56 s vs 6.72 s without it, within variance); with the new runtime 2/137 and 2/141, 0 wins. The slow gemma calls
  on serverless are slow for both copies (shared provider queue or long generations), so a duplicate at ~p90 does not
  answer first. It stays in the gateway, off, with its budget and metrics, for a provider where it does pay off.
- **Against Claude** (baseline of this file, not re-run today): success 54/54 vs 51–54/54; turn p95 4.66–4.88 s vs
  8.12–9.62 s; max 9.0–10.9 s vs 19.9–70.4 s; cost 1.36–1.44 vs 11.61–19.40 USD per 1,000 conversations.
- Two bench issues found and fixed on the way: replays after the bench's own back-off (its shared app rate limit or
  a token rotation) reused the caller's timer, so with a 15 s per-attempt timeout those replays failed instantly
  (4 runs dropped, not reported); and a synchronous token rotation stalled the other conversations.
